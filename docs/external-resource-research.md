# Creature data and combat automation after P06

**Decision brief · 25 November 2026 · Proposed for approval**

## Executive summary

1. **Qualify the library already in the checkout.** P06 is the last signed-off phase. The working tree also contains a versioned monster pack, XML importer, DM-only store and editor, template snapshots, requirements R41–R42, and a browser rehearsal. Rebuilding that work would buy little. Start P07 by exercising it against the P06 baseline. Extend its strict schema through a versioned reader once actual pack fields justify the change. [Plan and dated handoffs](local-multiplayer-plan.md) · [Pack types](../src/monsters.rs) · [Library rehearsal](../tests/monster-library.cjs)
2. **Use a common stat block and ability description, with the current owner applying each change.** An enemy can spend a legendary use in the host's room transaction. A familiar can spend its owner's command through the player's existing sheet. Both can use the same attack description. Sharing immutable inputs and pure calculations solves the duplication without moving either participant's live state. [Enemy rows](../src/party/initiative.rs) · [Companion cards](../src/combat/companions.js)
3. **Use Borealis as the first P08 build input, with the official English SRDs as the authority.** At the inspected revision its two CC BY packs contain 317 and 330 monster records across the correct chapter and appendix files. Open5e is a useful independent comparison and fallback. Budget for reconciling entries and checking the semantics of every enabled mechanic. This is substantially less work than writing two PDF parsers. [Borealis 5.1 coverage][b51cov] · [Borealis 5.2.1 coverage][b52cov] · [Official releases][wotc]
4. **Deliver Manual play before Assist.** Separate an announced attack, an addressed question, and a final delivery. An interruption can change or cancel a proposed outcome before anyone applies damage. Use the existing recipient claim, writer, receipt and correction paths for the final delivery. Keep the player sheet playable alone and all content available offline. [Room protocol](../src/party/wire.rs) · [Browser transaction](../src/combat/encounter.js)

### Foundry VTT D&D 5e

Foundry's NPC model extends a creature template with its own actor data. Attack and save activities have distinct data models, and save damage can depend on the result. That separation suits a monster's stat block and a PC's spell equally well. Foundry's implementations also depend on Foundry document classes, field APIs and roll configuration. Adopt the division between an actor, an activity and its consequences. The MIT software license permits selected code reuse with notices. The project's README separately identifies SRD material and per-asset licenses. There is no reason to distribute Foundry modules or its compendium with the tracker. ### Avrae implementation

An attack effect deserializes hit and miss branches. A save has separate result branches, and counter consumption is its own effect. Initiative effects carry IDs, interact with combatants and can depend on other effects. These are good patterns for a strike with an optional rider and for concentration-linked expiry. Avrae executes against its own combat context. Aurora must stop at a proposal where another owner has the decision. Avrae's code carries GPLv3 terms. Use the published ideas and independently implemented, bounded operations. [Attack][aattack] · [Save][asave] · [Use counter][acounter] · [Initiative effect][aeffect] · [License][alicense]

### Avrae automation documentation

The reference specifies target iteration, attacks, saves, damage, temporary HP, counters, text and initiative effects. An effect can tick at start or end, on the caster or target, with an optional parent and concentration relationship. Aurora can represent a failed save followed by damage and a condition using a few typed fields. Imported expressions, recursion, author scripts and automatic traversal across remote characters would add an interpreter and conflict with manual resolution. ## Proposed creature model

Keep the pack envelope and the existing template snapshot. Extend the format only for information that the stat-block reader, a filter or a supported mechanic consumes. Keep other authored sections as ordered, titled text. Rust owns pack decoding and DM instance validation. The browser renders the normalized view. No player profile migration is needed to read a stat block.

| Record and identity | Fields and responsibility |
| --- | --- |
| **Pack and source** | Stable pack ID, schema major, rules family (`2014`, `2024` or author-labeled homebrew), publication/revision, display source and attribution. Bundled manifests add language, license ID/URL, upstream commit and files, input hashes and conversion notices. Keep source entry ID and page **or** section/entry locator per monster. A local installation revision is distinct from a reproducible build digest. |
| **Creature template** | Key by (pack ID, template ID). Preserve name, size choices/swarm size, type/tags, alignment, exact fractional CR and printed notes. Include printed AC alternatives and qualifiers, HP average/formula, movement modes/units, six abilities, explicitly supplied save/skill modifiers, senses/passive, languages and qualified damage/condition defenses. Carry printed initiative modifier and score separately, PB, XP/lair XP and gear when supplied. Cross-edition aliases may aid search later. Two entries always keep distinct keys. |
| **Abilities on the template** | Ordered traits, actions, bonus actions, reactions and legendary options. Each has an ID unique within the template, name and complete readable text. Preserve section preambles, additional headings, trigger text and source exceptions. Only attached, validated mechanics participate in Assist. A conditional defense, spell list or lair effect can remain wholly readable. |
| **DM encounter instance** | Existing encounter ID and opaque row ID, optional immutable template snapshot including edition and revision, editable private name/alias, HP, AC, conditions, initiative and action notes. Store uses spent, recharge availability, legendary pool and reaction use by instance and ability/pool ID. Hand-entered enemies can have no template. Add N initializes independent counters. Preserve P06 Duplicate semantics by copying the selected instance's current values under a fresh row ID, including the new counters. Exclude pending windows, offers and external associations from the copy. |
| **Owner-controlled participant** | Project shared descriptive fields from an existing companion template/card when useful. Retain card ID, owner, command cost, turn choice, effective stats, resources, duration, zero-HP behavior, local edits and undo on the player sheet. Runtime targeting maps member + local card ID through P06. A PC supplies local effective stats to an ability without becoming a monster record. |

**Edition and migration.** Numeric zero, a missing number and a conditional value have different meanings. Keep display text alongside typed values and parse exact CR fractions for ordering. A missing save is unknown for automation unless that source explicitly defines its derivation. The 2024 printed initiative can differ from a Dexterity-only estimate. The target player's concentration rules remain their own setting even when the enemy comes from another edition. The strict v1 decoder rejects extra fields. Introduce a v2 reader with explicit version dispatch, defaults for genuinely absent optional fields, and a v1-to-current in-memory conversion. Dispatch stored snapshot reads as well as pack imports. Older roster rows may have no template or schema tag on the snapshot. Read them safely, do not rewrite a live fight on pack replacement, and fail closed on an unknown major. Use original v1 files, backups, named positions and a hand-entered P06 room as compatibility fixtures. [v1 types](../src/monsters.rs) · [Room deserialization](../src/party/store.rs)

**Companions, summons, familiars and mounts** can read the same creature description. Acting with the owner, taking a separate turn, vanishing at zero HP and requiring an owner's bonus action are role-specific policies. A commanded cannon, a temporary summon and an independently acting mount can therefore differ without three stat-block models. **Wild Shape** needs a future association between a player and a form template. The player retains their identity, and edition-specific HP, replacement/retained stats and reversion require a separate owner transaction. A second initiative row or a destructive copy over the base character would break that contract. P07 only needs reusable data and a regression for the existing cards. [Companion importer](../src/companion.rs) · [Owner action economy](../src/combat/action-economy.js) · [Companion regression](../tests/companions.rs)

**External tokens.** Keep the opaque encounter and instance IDs stable through rename, hide, reorder, save and same-room resume. A future DM-owned binding can map (provider, external room/scene key, item ID) to (Aurora encounter ID, instance ID). It can be removed or rebound if a token is deleted, copied or moved. Across room import, require explicit remapping. Owlbear items have a read-only ID and extension metadata is shared. Keep private fields and credentials on the Aurora side. These identifiers suffice through P10. Defer the binding table, SDK, token metadata writes and network integration. [Owlbear item reference][owitem] · [Metadata guidance][owmeta]

## Proposed ability model and adjudication

Use a small typed description plus a recorded resolution. Keep the source text available throughout. A draft can be abandoned before commitment. The resolver calculates suggestions from supplied values and returns a result the owning handler can commit. A full actor object, a scripting language or a universal network command is unnecessary.

| Part of an ability | Proposed meaning |
| --- | --- |
| Identity and timing | Template-scoped ability ID, name, category, trigger or timing window, target count/selection, reach or normal/long range. A free-text trigger always permits manual play. |
| Resolution | An attack records a nullable natural die and a separate total. A save records ability, DC and per-target outcome. Simple rules specify hit/miss or success/failure consequences, including half/none/full damage. A known rider may require an additional save or a confirmed predicate, such as target size. Unresolved predicates prompt the table. |
| Consequences | Ordered typed damage components with optional dice and printed average, healing or temporary HP, an optional condition or bounded modifier with source, target, stacking and duration. Support only named slots such as AC, attack or damage bonus and existing stacking rules. Unsupported consequences remain visible in the text and can be recorded manually. |
| Costs and recovery | Optional action/reaction cost, ability use or named shared pool, per-option legendary cost, refresh rule or recharge die/threshold. Instantiate counters per enemy. Respect printed limits and triggers, including lair qualifications or once-before-next-turn clauses. Show a manual spend, roll, skip or correction for ambiguous refreshes. |
| Multiattack | Ordered references to strikes, with repetition bounds. Repeated leaf IDs are legal. Create a fresh strike ID and reaction window per strike. Replacement choices can be selected manually. Reject cycles and unresolved references before use. Charge the parent action once and charge a child resource only when its own terms require it. |
| Recorded outcome | Stable action, strike and target IDs, chosen inputs and modes, adjudicated outcome, agreed damage components/total and offer ID when applicable. Persist the actual roll/result before retry. Separate damage events preserve separate concentration checks. Store roll details only for their intended audience. |

**A concrete boundary.** The two wolves above both normalize to a melee attack with a piercing component. The 5.1 rider calls for a Strength save. The 5.2.1 rider tests size. If the recipient shares only a name, the player can answer the rider privately or record it by hand. A `save_dc` field without an ability or an outcome, or a partially parsed bite, must never silently omit the rider or invent a save. A DM can always enter an agreed damage total. A player with a private resistance can give the table the adjusted amount or decline and record the result locally. [SRD 5.1][wolf51] · [SRD 5.2.1][wolf52]

**Player and monster reuse.** Share bounded dice parsing/rounding, outcome descriptions, typed components and test vectors. If both browser surfaces need the same pure calculation, package one small browser module through the existing asset paths. Rust keeps validating external input and committing host commands. The player's Extra Attack, Sneak Attack, spells, infusion stacking, costs, target selection and concentration remain in their existing handlers. Extract a state-only function from the current incoming-damage form so the local dialog and an accepted remote offer perform the same HP absorption, zero-HP behavior, concentration DC/prompt and log update in the receiving transaction. Do the same for a reaction cast when first needed. Avoid calling UI click handlers or charging both a generic resolver and the sheet. ### Interruption and delivery contract for P09

1. **Declare.** The DM chooses a source instance, ability or plain text, strike, targets and alias-safe public wording. Manual defaults to physical dice and spoken answers. Committing the action spends the source cost once and captures the action ID. Abandoning its preview spends nothing. Persist source use and any initial requests in the same host transaction.
2. **Ask.** An addressed question is a durable pending decision with a strike, target, window ID and revision. The player may answer hit/miss/save, pass, or use an eligible reaction while sharing name only. A known current, permitted AC can inform a provisional suggestion. Missing, stale or withdrawn information routes back to a question. The public turn stream gets neither the question nor the answer.
3. **Interrupt.** Revalidate the trigger and resources under the owner's writer. A Shield decision atomically spends the player's chosen slot/reaction, records the linked effect, and stages the reply under a stable ID. The DM needs the revised outcome, never the player's private AC or resource list. Re-evaluate the same strike. A clock event that advances past a pending trigger makes it subject to explicit adjudication. Do not apply an old reaction to a new turn on reconnect.
4. **Finalize.** The DM can record the spoken answer, accept the reply, cancel the unfinalized strike, or explicitly override. Only one revision can win a race between a response and closure. Never infer consent or a failed save from silence. Lost races after a player has committed a reaction surface for owner correction. Confirmed source costs can be corrected explicitly. Commit one final addressed damage offer per affected target **per damage event**. A miss/cancellation closes with no HP offer. One area roll can yield different final totals per save. Digital roll, AC comparison and damage suggestions each have their own switch.
5. **Apply and correct.** The recipient claims and records the final amount, temp HP absorption, applicable concentration outcome and receipt together. A storage failure leaves a retryable claim. A lost acknowledgment reuses the consumed ID. Each distinct hit can prompt concentration even when one attack action generated both hits. A recipient can decline or explicitly reconcile a prior claim after restore. A DM can close an unanswered window, continue other targets or record that damage was handled at the table. Corrections after delivery use the existing recipient-owned reversal/correction semantics. A named save, new room, backup or Undo must never resend a completed attack.

The host serializes these transitions, validates role and IDs, and stores only addressed conclusions and offered mechanics. Version new wire shapes explicitly and reject or capability-gate incompatible helpers before action creation. P01 already defines `Effect::Damage(NonZeroU32)` and includes synthetic damage exchanges. The player offer UI filters damage out, and its non-grant apply branch currently treats anything other than healing as temporary HP. Widening the filter alone would turn damage into temporary HP. Add explicit effect dispatch and a recipient damage handler. Use a new question/reply contract for interruptions. `Room::send` permits one offer per (sender, recipient, action_id), so give distinct strikes distinct delivery action IDs linked to their parent action. A zero outcome needs no damage offer. [Player decision handler](../src/combat/party.js) · [Offer uniqueness](../src/party/model.rs) · [Wire fixtures](../tests/fixtures/party-exchanges.json) Order mechanical messages against P06 clock deliveries, including after missed polls. Persist the roll once, use a separate ID for each target decision, and make reordered or duplicate replies harmless. [Wire types](../src/party/wire.rs) · [Command replay](../src/party/store.rs) · [Clock consumer](../src/combat/party-initiative.js)

**Expiration.** Use the existing effect source, target and anchor semantics for start/end, rounds, elapsed game time, rest, concentration and manual removal. Owner-turn companions keep their existing boundary mapping. End effects on a removed target and let the owner end or reanchor other effects tied to that turn. A paused question has no wall-clock duration in the rules engine. Source/target removal, cancellation or a missed trigger needs an explicit outcome. On the host, recover enemy reactions, legendary pools and recharge eligibility exactly once on the printed boundary. Save a chosen recovery result with the command. Pointer corrections, reordered ties and named resume do not repeat it. ## Phase estimates and acceptance

Estimates are engineering days for one maintainer familiar with the code, including targeted tests and a handoff per assignment. They assume the working-tree library is retained, the pinned data can be converted, and existing Windows packaging is available. Corpus discrepancies and crash/replay behavior are the largest uncertainties. Order below matches the [proposed phase plan](local-multiplayer-plan.md). Each row can be rehearsed at its normal entry point before starting the next.

**Tradeoffs visible at release.** A snapshot costs more space than a library pointer, but allows offline play after deletion/replacement. Measure Add 100, DM poll bytes/latency and named save/restart using the largest actual pack block. The current validator limits one creature to 128 KiB and the library limits a pack to 16 MiB. Keep the compact player projection. If measurements force deduplication, use immutable host-local snapshots keyed by content with the same observable behavior. A persistent reaction window costs more than a synchronous dialog because there are two writers and no global Undo. Spend that complexity only on an explicit, addressed decision. Scoped Assist leaves unusual powers manual, but the table can still resolve their complete text. ## Explicitly deferred until after P10

- End-user Open5e/5etools import wizards, a pack marketplace, online search or automatic updates. Reconsider self-contained adapters if the native pack and XML paths leave a demonstrated need.
- Applying a form to a player, edition-specific Wild Shape/reversion, mount control automation and generalized summoning. Preserve the IDs and companion policies needed to add them later.
- Owlbear SDK, token binding UI, map geometry, movement measurement, token synchronization and external credentials. Preserve instance identity now.
- General rule scripting, recursive reaction stacks, automatic legendary/lair AI, universal PC action conversion and official packs beyond the two English SRDs. A complex action remains playable through Manual.
- Content-addressed snapshot storage or a shell migration. Revisit only with measured storage/latency costs or a separate desktop decision.

## Decisions requiring approval, in priority order

1. **Schedule P07A as qualification of the existing work**, then P07B as a compatible schema extension. Adopt common descriptive data with separate player and DM runtime ownership.
2. **Approve the two pinned Borealis CC packs as the P08 starting inputs**, with the official PDFs as the release authority, a per-entry ledger, build-time conversion and offline attribution. Open5e serves as a cross-check.
3. **Approve Manual-first P09 and its ownership contract.** Final damage uses recipient claims and receipts. An addressed interrupt stays provisional, never auto-accepts, and supports explicit closure and owner correction. Approve the four independent P09 handoffs.
4. **Keep P10 as the release gate.** Require the legacy, privacy, crash/replay, offline package and desktop checks. Carry outstanding physical-device checks explicitly. Keep external import UIs, form mechanics and Owlbear integration deferred.
