# Architecture

## Shipped component map

The Windows Forms launcher invokes `combat-sheet` to generate a local player sheet. For a party, it starts `aurora-party` and attaches a loopback capability to the player sheet or opens a separate DM dashboard. Guest helpers connect to the host over TLS. The player browser owns character mutations and local undo. The host's Rust room service owns membership, addressed deliveries, shared initiative, and enemy instances.

## Planned desktop shell

The proposed Tauri shell would provide the window, file dialogs, and native bridge. Svelte and TypeScript would render the sheet and call named Rust commands through `invoke()`. The Rust combat core would handle session updates and return a view or error. Its tests can run without a desktop window. Use the shipped component map above for current changes.

Aurora is the source of character build data. The tracker owns the session and layout, so re-import can update available options without resetting the fight. Companion behavior comes from imported definitions and editable cards. The Artillerist’s cannon exercises the same companion system as a ranger’s pet or a summon.

## Home Wi-Fi multiplayer

P01 implements the host-side room authority in Rust. P02 connects helpers to it from the Windows launcher. Players own their character mutations and choose what the DM may inspect. The DM host owns the shared encounter clock and individual enemy records. [Multiplayer and DM implementation plan](local-multiplayer-plan.md)

`party::RoomService` is the entry point for native dispatch. Call `execute` with a verified principal and a versioned JSON command. The native layer supplies local-host authority or an opaque pairing identity bound to a room and character. It owns credential protection, transport authentication, and mapping a verified connection to that identity. Create chooses the host mode. Join assigns a fresh member UUID. The shipped initiative UI sends revisioned edits to the DM room's encounter. Its position and clock events own turn boundaries. The earlier `SetRound` command carries a separate display-only round value.

`aurora-party init` initializes or reopens `%LOCALAPPDATA%\Aurora Combat Tracker\party.sqlite3`. An explicit database path supports isolated runs. SQLite schema version 1 stores a room snapshot, command journal, and per-member delivery streams. An immediate write transaction serializes competing commands and commits the room, addressed events, and command result together. The journal binds each room and command ID to its principal and typed request. Replaying a journaled command returns its original receipt or rejection. A disconnected sender can retry an outgoing action or grant end after resuming its lease. A storage failure rolls back the transaction and allows the same command to be retried.

`poll` reads the current member projection and up to 128 events after that member's cursor from one database snapshot. Clients advance their cursor after processing each event. Offer events go only to the sender and recipient. `publish` replaces the owner's entire DM inspection in memory. A disconnect marks the last publication stale through the member's offline flag. Resume clears it for fresh publication. Leave, close, and host restart discard the applicable inspections. After restart each participant issues a fresh resume command. An old command retry only returns its saved result.

Leaving expires pending HP offers involving that member. Closing expires every pending HP offer and ends membership. Either action preserves HP claims and receipts and ends outstanding or accepted attack grants for the affected members. A paired participant can still call `reconcile` for their addressed offers, and the original recipient can finish a claim. Reconciliation exposes offer status without the recipient's resulting HP or other character changes. The synthetic exchanges exercise the same Rust dispatch as the Windows helper. [Protocol examples](../tests/fixtures/party-exchanges.json)

### Windows launcher and party transport

The launcher starts `aurora-party serve` with its configuration on a private stdin pipe. The helper returns a fresh loopback capability on stdout and exits when the pipe closes. The launcher embeds that URL in the generated sheet on every refresh or opens a local DM lobby without running the importer. Party requests require the capability and the file origin (`null`). The helper's role determines which actions the view may call. Aurora refresh continues to use the launcher's separate bridge.

The launcher uses a Windows mutex and activation event scoped to the signed-in user and desktop session. The current sheet and DM dashboard renew a shared lease on the launcher's token-protected loopback bridge. The hidden launcher checks for five minutes of inactivity and grants browsers time to check in again after sleep. Before closing a hosted session it checks the room's state through the Party helper so browser or network interruptions do not end a live room. Closing the launcher closes the helper's stdin first. A Windows Job Object set to terminate its members when the launcher handle closes adds crash cleanup, with the stdin pipe remaining the fallback in environments that restrict job assignment.

A host binds TLS to one selected IPv4 address. An invitation carries the endpoint, room ID, protocol version, random admission secret, certificate and SHA-256 fingerprint. The guest's Rust HTTP client trusts the invited certificate for the party service name, connects to the advertised address, and disables redirects and proxies. It checks an existing room's saved fingerprint before changing endpoints. The existing LAN path `/v1/party` accepts protocol 2 packets. Guests can join, resume, poll, leave, submit initiative, publish allowed details, and exchange addressed offers and replies. The host derives the paired principal from the guest's native bearer credential. Host and DM commands have a local dispatch path.

The Windows user’s DPAPI key protects host keys, invitations and peer credentials in the launcher’s separate `party-bindings.sqlite3`. Bindings are scoped by local character path (or the DM profile) and room. Pending admissions retain the identity needed to retry. Explicit resume uses the last active binding. Retired bindings remain local for future receipt reconciliation. The host reuses its certificate and port on resume. A guest helper maintains a cursor-based long poll until the launcher stops it. The host marks guests offline after ten seconds without renewal. The helper cursor tracks roster display within its process. Each sheet also persists its own cursor for mechanical clock deliveries.

### Recipient-owned healing and temporary HP

The room service routes offers and returns the offered amount, source and status to the two members involved. The recipient's sheet claims the offer before applying its existing owner healing or temporary HP rules. The encounter transaction writes the updated snapshot and the consumed offer ID into the same storage envelope. The browser sends acceptance after that write succeeds. Capped healing and a smaller temporary HP offer still get durable receipts. Undo restores the previous HP snapshot with the consumed ID intact. When an acknowledgment is lost, the sheet can resend it using the local receipt.

Web Locks serialize the claim, local write and recipient decisions across tabs. Browsers without Web Locks use one active writer through an IndexedDB read-write transaction. Party delivery requires browser storage and one of these writer mechanisms. Both routes use the encounter transaction shared with local updates and backup restore.

Version 1 backups omit the live receipt ledger. Restoring while attached invalidates the sheet capability at the local helper, preserves existing local receipts and records a restore marker to invalidate older tabs. Resume from the launcher to reattach. A claimed offer with no local receipt presents Apply offer, Already handled and Decline. The helper can also resume a closed room for addressed receipt reconciliation. Membership remains ended.

### Casting and granting to party members

Combat and Quick Actions use the same cast, point-spending and Protector handlers. The Rust projection identifies healing mechanics and target counts. The sheet collects the actual roll. Inside the encounter writer, `party-actions.js` resolves room and member IDs, applies local HP rules and stages one send command per remote target. One storage write commits costs, local effects and the outbox. The commands share an action ID and have independent retry IDs. Only a successful helper response retires a command. Reloaded sheets retry commands for their current membership.

A committed outgoing action starts a new local undo history. Session → Party supports withdrawing pending offers and asking a recipient to reverse an accepted HP change. The recipient controls mechanical corrections. The sender can correct their own resources and turn counters.

A grant offer carries its opaque grant ID, source label, weapon or spell category, attack and damage bonuses, stacking rule and end rule. The recipient selects an attack from their own sheet. Its local pin feeds the same modifier calculation as an owned assignment. Imported infusions use the highest matching bonus. Custom imbuements add their modifiers. The private selection and live grant bindings are excluded from portable backups.

Source assignments live with the caster. Each encounter commit reconciles removal, replacement, linked-effect expiry and rest resets with the outbox. The room records ended grant IDs by issuer, so an end arriving before its send also prevents acceptance. A recipient reconciles the final addressed status after reconnect, recording an end receipt and removing the modifier from current state and retained undo snapshots.

### DM dashboard and sharing

The launcher packages the DM dashboard as HTML, CSS and JavaScript assets and writes a local view for Host as DM and DM resume. It uses the same loopback capability and room poll as the Party controls. The importer is bypassed for the DM. The overview AC preference stays in the DM browser. The overview and read-only inspector render text from the latest DM projection and clear revoked fields on the next poll.

The player sheet stores the sharing choice locally by profile, room and member. An explicit allowlist builds the publication from current encounter state, effective combat stats and the rendered rules for the permitted categories. The browser coalesces redraw events and skips identical publications within a connection session. It reads the current choice and sheet state under the encounter writer before sending. An open sheet republishes after resume using the current choice.

The guest helper attaches a sequence number to each typed publication. The host assigns a new publication session on resume and holds the latest sequence and inspection in memory. This prevents a delayed request from restoring withdrawn fields after a downgrade or reconnect. The published values stay out of the command journal, events, backups and SQLite room snapshot. The host's DM projection is the only response with inspections. The loopback guest response exposes the player's own publication session and the public roster, while leave removes the inspection from memory.

The 2026-11 UI rework kept every control ID, accessible label and button name, so the packaged rehearsals still drive the same controls. The clickable turn list (`#dm-turns`) is a pointer shortcut that sets the labelled `#dm-order` select; the select remains the keyboard and assistive control, so the list is `aria-hidden`. Stat blocks keep each line's text as "Label · value" and only hide the separator with CSS. Icons are an inline SVG sprite of game-icons.net symbols (CC BY 3.0, credited in the dashboard footer and [third-party assets](third-party-assets.md)), so the offline dashboard needs no extra asset files or launcher resource entries.

### Shared initiative and turn boundaries

The DM dashboard and the player’s Initiative dialog send revisioned edits to the Rust room service. A transaction commits the encounter, command receipt and addressed clock events together. A repeated command ID returns the original result. An edit based on an older encounter ID or revision asks the caller to refresh. Named saves capture row IDs, tie order, round and current actor. Ending pauses that position. New encounter clears the working roster. A player leaving also leaves saved rosters in that room.

Portable encounters (P10) reuse that position. `Fight::export` writes an `aurora-encounter` version 1 file with each row's ID, score and a portable actor. Enemies carry their record, template snapshot and action counters with an empty history. Player rows become seats with the exported name and companion list, and separate companion rows refer to their seat by row ID. Member UUIDs never enter the file because they are room credentials in practice and mean nothing in another room. Recorded strikes are dropped because the room-level review, window and damage ledgers they point to stay with the source room. Import is a DM-only `Edit::Import` on a stopped encounter. It carries the file and an explicit seat-to-member map, validates the whole file (format, version, unique IDs, enemy limits, template snapshot, counters against the snapshot's rules, companion links and pairing) before replacing anything, and assigns a new encounter ID. Pairing names only active members of the destination room, at most one seat each. Row IDs are kept so references stay stable across a round trip. The import goes through the same transaction, journal and stale-window handling as Load. The dashboard prefills a seat only for a single same-name player, and the DM confirms every seat. The loopback request limit of 1 MiB caps the file size.

Each enemy is an independent instance. Grouping copies the selected score to enemies with the same private name, preserving their IDs, HP and notes. The host builds the player projection before transmission. Hidden rows expose an opaque ID and “DM turn.” Revealing a row shares its alias and initiative. The DM projection alone contains the enemy record.

The host sends a clock delivery to each participating sheet, mapping its member and companion IDs to local turn keys. Starting enters the first turn. Next Turn applies the outgoing end, a six-second rollover when appropriate, and the incoming start through the same boundary functions as solo initiative. A manual time advance uses the existing duration functions. Pointer corrections and named-position resumes carry position only.

Two edits let the table run turns without the DM reaching for each sheet. `Edit::Seat` is DM-only: it places an active member of the room in the order with a score rolled at the table, or updates that member's existing player row, and keeps their companions. The player can still resubmit from the sheet, which replaces the score. `Edit::EndTurn { id }` is player-only and advances exactly like Next, but only when the current row is that player's or one of their companions' and its ID matches, so a stale click cannot end someone else's turn. Both go through the same revision check, transaction and stale-window handling as Next and Submit. The dashboard lists active members without a row under "Not in the order yet" so the DM can see who still needs a score.

Timed enemy conditions (R77) live on the enemy record as `timers`, apart from the free-text conditions, because the dashboard's enemy edits (Edit enemy and quick HP) send the whole record and must not drop or fight over them. `Edit::AddTimer` and `Edit::RemoveTimer` are DM-only, and `Edit::Enemy` copies the existing timers like it copies the template snapshot. Each timer counts the turn start or end of its anchor row, the enemy itself by default, in the same pass that resets monster action counters, plus every round of advanced time. An anchor that has left the order falls back to the enemy. Ended timers stay at zero until the DM clears one, so an expiry is noticed rather than silently dropped. They are part of the enemy record, so the player projection never carries them and portable encounters keep them.

On a player sheet in a DM room, the combat rail follows the shared order whenever an encounter exists, joined or not. It shows a Party encounter banner with the other players, a Join form until the player has a row, and End Turn only on their own turn. Next Turn, Start and End Encounter, and the solo combatant editor are hidden there because the DM owns the order. Leaving the encounter from the Initiative dialog returns that sheet to solo turns for that encounter, as before.

The sheet consumes clock deliveries in cursor order under the encounter writer. One storage write commits the mechanical changes and the room/member cursor and starts a new undo history. The sheet keeps its solo roster and saves its solo pointer while the DM controls initiative. A backup exports the solo pointer. On reattachment, the last consumed delivery can supply the shared position without repeating its effects. The owner can explicitly restore fields changed by the latest mechanical clock update if those values still match the recorded result. This leaves the authoritative turn and delivery cursor intact.

### Offline monster library

The launcher packages the Monster library alongside the DM initiative controls. The DM helper stores packs in `monster-library.sqlite3` under launcher app data. The helper exposes the library through the DM’s loopback capability. Pack data stays on the DM machine. Only the DM projection includes enemy stat blocks.

The native pack envelope has `schema_version`, `info` and `monsters`. Rust reads v1 and v2 into a common stat block, with optional fields defaulting to unknown and numeric zero preserved. V1 installs retain their schema when read, edited or exported. New homebrew and Aurora imports use v2. Existing room rows can be template-free, and an unversioned snapshot reads as v1. New v2 snapshots record their version. Unknown majors fail at the typed reader. The library continues to use the same SQLite table.

V2 adds optional pack license and per-template source entry, page, section and version. It preserves mixed sizes, alignment, printed initiative score and modifier, conditional AC alternatives, proficiency bonus, XP, gear, qualified stat notes, legendary preambles and ordered sections. Movement, senses and qualified defenses retain their published wording. The DM reader sorts numeric CR filters by fraction and uses the printed initiative score as the editable Add default. It initializes encounter AC from the base value.

Each rule keeps its template-scoped ID and full text. V2 can attach a save ability and DC with explicit full, half or zero damage branches, and a legendary action can carry its cost. Existing range, damage components, use/reset and recharge fields carry forward. V2 damage dice accept one term of 1–100 dice with 2–1,000 sides and an optional signed modifier up to 10,000. Use the rules text and an optional manual note for unresolved riders. V2 multiattack can reference up to 32 ordinary leaf actions in order, including repeats. Rust rejects missing and cyclic references before installing either pack version. The stat block and action descriptions are independent of party state and can also describe player-owned companions. Companion cards retain their own IDs, live stats, turns, commands, durations, edits and undo.

Replacing a pack requires the installed revision shown in the conflict preview. The save validates the entire pack and uses one conditional SQLite write. Separate pack IDs distinguish editions with the same creature names. Add to encounter creates up to 100 independent rows in one room transaction, each with a private immutable copy of the selected template and installed revision. Instance edits, named rosters and helper restart retain the snapshot, including after a pack update.

Aurora folder import reads selected XML files in relative-path order and uses the existing content index to resolve creature-shaped Companion definitions, appends and linked rules without loading a character. It keeps the source entry ID and published version where available. Supported literal stats become structured values. Formulae, unresolved links and imported action text remain readable for table adjudication. The importer reads the selected files without modifying them.

5etools import (`src/fivetools.rs`, helper route `monsters/fivetools`) converts one bestiary file's `monster` list into a v2 pack for the same review and save flow. It renders `{@tag}` markup as printed text and maps size codes, AC forms, HP, speeds, abilities, saves, skills, CR and XP, alignment codes, spellcasting and every action category. Unambiguous `{@hit}`, single `{@dc}`, `{@recharge}` and "Costs N Actions" values also fill the structured attack bonus, save DC, recharge and legendary cost. Damage stays in the rules text, because 5etools prints conditional riders inline. Records that inherit through `_copy` are skipped and listed in the review rather than guessed. Lair actions live in separate 5etools files and are noted on the stat block. A 2024 edition pack derives printed initiative from Dexterity when the record omits it. IDs are `5et:<name>.<source>`, so re-importing the same file into the same pack ID keeps template IDs stable.

#### Bundled English SRD monster packs

One converter builds the native v2 packs for SRD 5.1 (2014) and SRD 5.2.1 (2024), using edition-specific pinned Borealis inputs and the English Creative Commons PDFs. It checks SHA-256, joins stable IDs to the official entry and page ledgers, applies reviewed corrections, and writes deterministic JSON in official order. Rule IDs use the category and base name. The source audits check printed rule text and the fields used for encounter initialization. [2014 source review](srd51-pack.md) · [2024 source review](srd521-pack.md)

The Windows helper embeds and validates both packs through the Rust reader used for imported packs. On the first DM library request it independently installs each missing pack ID. The conditional inserts allow concurrent opens and preserve installed packs and local replacements. The 2014 pack remains the default. The library labels results with the selected pack's edition. DM initiative and the stat-block inspector read the edition and published source from each instance snapshot. Installing or replacing a pack leaves the copied snapshot and its SQLite installation revision intact.

Entries initialize encounter HP and unconditional AC. The 2024 preview also carries the printed initiative modifier and score as distinct fields and uses the score as the editable Add default. Alternative sizes participate in each applicable size filter. The bundled rules use full readable text for table adjudication, including conditional riders, save branches, multiattack substitutions, and lair use limits. **Pack credits** and exported metadata carry attribution, upstream provenance, and CC BY 4.0 license references. The Windows package includes both notices files beside the executables.

### Manual monster actions

The Host as DM dashboard opens the acting enemy's rules beside initiative and allows a selected enemy's reaction or legendary action to be entered out of turn. The browser keeps a preview local and supplies stable action and strike UUIDs on commit. Rust validates the source, ordered strike rules, targets and available costs, then stores the action and its cost in the same revisioned room transaction. Ordered template strikes can repeat and each has its own target. A text-only rule can use manually added strikes. The existing command receipt handles retries. Recorded totals, rulings, target details and counters appear only in the DM projection.

Action state lives with the initiative row and defaults to fresh values for older rows. Template snapshots retain the printed rules. The DM can configure a text-only cost, limited-use reset, recharge threshold or legendary budget and can correct current counters without rewriting a past action. Legendary capacity is entered per enemy because the printed capacity can depend on its circumstances. The DM adjudicates reaction triggers, legendary timing and situational rules at the table. Named saves preserve the entire action state, including queued recharge rolls. Duplication copies configured counters, drops queued rolls and starts an empty history under a new row ID. The dashboard shows the latest 20 records per enemy.

The same turn operation that creates the P06 clock events processes enemy recovery in outgoing end, round advance and incoming start order. Ordinary action slots recover at the start of the enemy's turn. A queued recharge roll is consumed at that start and its result is retained. Limited uses and legendary budgets can recover at own start, own end or a round advance. Rests and unrecognized reset wording use manual correction. Pointer corrections, named-position resumes and elapsed seconds leave per-turn counters alone. Manual rulings leave player HP and reactions with their owners.

#### Delivering a final damage amount

The DM records the strike first and then confirms its final amount in Recorded actions. The host resolves the chosen player to a room member at recording time, including members who have yet to submit initiative. It uses the strike UUID as the wire action ID and stores the parent action, strike and offer linkage in a room-level ledger. Finalizing a strike and sending its offer commit together. The ledger survives named-roster loads so an earlier snapshot cannot reissue a finalized strike. Misses, zero amounts and results handled at the table create no offer. Non-player targets are resolved at the table.

The addressed offer reuses `Effect::Damage` and carries a generic DM label, the final amount, an opaque strike ID and receipt status. Damage is created through the DM initiative command. Generic launcher sends still reject damage. The room's DM-only projection links offers to recorded strikes, and the dashboard's Party section lets the DM withdraw pending offers or request a recipient correction. A recipient using an older sheet needs the updated package to see damage offers.

The player claims damage through the same writer and receipt path as healing. The local damage form and party acceptance share `concentrationControls.applyDamage`: temporary HP absorbs damage first, the original final amount drives the concentration DC under the owner's saved rules, reaching zero ends concentration, and the damage log commits with the receipt. Missing HP blocks application and leaves the offer available. Undo restores HP, concentration and log state while retaining the receipt. An already claimed offer stays recoverable after browser or room closure.

#### Save and reaction questions

`src/party/interruptions.rs` defines the question, opaque window ID, generation and reply. The room stores the current generation and ruling per strike outside roster saves. Host edits use the initiative revision and reject damage finalization while a question still needs a ruling. Accepted replies and their overrides leave an auditable command record. A replay of an acknowledged command returns its original receipt. New replies to a closed or replaced generation leave its ruling intact. A real turn advance makes unanswered attack and Magic Missile triggers stale. Save questions can span turns and disconnects. Source or target removal and encounter replacement require table adjudication. Tie edits and pointer corrections preserve viable questions.

The owner checks the authoritative window and their pending clock deliveries before spending. Under the sheet writer, `party-windows.js` revalidates the prepared Shield reaction and slot, then saves its spend, effect, receipt and reply outbox in one write. Shield uses the existing owner-start effect boundary. The player chooses the outcome at the table. If the window closes while a saved reply is in transit, the host rejects the late reply and the sheet explains how to undo or manually correct the spend. Other reactions with unresolved mechanics use table adjudication.

The recipient projection carries the window ID, generation and question kind. The reply carries a ruling and whether a reaction was used. Addressed replay events carry only a change marker. Raw rolls, private labels, saves, defenses, slot choices and spell names are outside these exchanges. The public announcement list contains only text entered explicitly by the DM. LAN packets require protocol 2. Resuming a saved room with the updated package preserves its certificate, port, members and data. Version 1 helpers or invitations receive an incompatibility error.

#### Bounded Assist

Manual and Assist use the same DM preview, strike records, reaction windows and final damage offers. The preview holds the natural die and any approved digital total separately from the entered table total. The host stores them with the strike and its parent cost. Reviewing an unfinalized strike preserves its identity and any saved digital roll, including while a different strike waits for a reply. A natural 20 is a critical candidate. A natural 1 is a miss candidate. An entered total alone has no natural-die meaning.

The dashboard uses only an online player's currently shared effective AC or the DM's known unqualified enemy AC. A withdrawal of sharing or changed comparison removes an unconfirmed ruling suggestion. No defense value goes into the strike record. Typed save branches select the full, half or zero amount after the DM confirms the outcome. Unsupported damage terms and unresolved riders stay table calls. Suggestions for final damage require confirmation of resistance and other modifiers, and the DM can enter a custom final number.

`launcher/dm-monster-assist.js` contains the bounded browser calculations. The room stores the normal and critical raw damage totals before the final amount is sent. Strikes for the same typed save in one action can reuse a saved raw roll and apply different branches. The room links each final offer to its original strike and leaves player HP, saves and reactions with their owners. Text-only packs retain their rules for manual adjudication.

### Owlbear Rodeo link

Stage O1 of the [Owlbear Rodeo plan](https://claude.ai/artifact/JNNdKTKdKgaRoF34zaqj7m) links one Owlbear room to the DM's room. The Stage 0 rehearsal on Chrome 158 showed that Owlbear does not delegate `loopback-network` to extension iframes. Chrome therefore denies a direct `fetch` from the extension to 127.0.0.1 without a prompt. The extension reaches the helper through a pop-up bridge window instead.

A DM helper binds a second listener on `127.0.0.1:47831`, or an ephemeral port when that port is taken. It never binds a LAN address. `GET /obr/bridge` serves the bridge page (`src/owlbear-bridge.html`). The extension's popover opens it with a click. The page keeps a handle to the Owlbear tab (`window.opener.top`) and posts a hello to every frame in it. It addresses each message to an allowlisted extension origin, so the browser drops copies for other origins. The extension's background page claims the window and sends requests through it. The page forwards only `pair`, `status` and `table` to `POST /obr/api/{action}` as same-origin fetches. An Owlbear reload replaces the extension frames, so the page says hello again after 8 seconds without traffic, and the new background page reclaims it with its saved token.

The API requires a `Host` of exactly `127.0.0.1:<port>`, which defeats DNS rebinding, and an `Origin` equal to the bridge page's own. Every action except `pair` needs a session token. The DM dashboard shows a six-character code from an unambiguous alphabet. A correct code is used once and returns a token. Five wrong codes replace the code. Tokens expire after 12 idle hours, at most four live at once, and the dashboard's Unpair Owlbear revokes them all. Pairing lives in helper memory, so restarting the helper requires pairing again. The bridge page has a CSP of `default-src 'none'`, with inline script and style only, `connect-src 'self'` and `frame-ancestors 'none'`.

`RoomService::table_view` is DM-only and returns the player-safe projection from `Fight::table_view`. That projection carries row IDs, kinds, revealed names, member and companion IDs, and the turn pointer. For enemies it adds a down flag (HP 0) and the monster template's key, name and size, so the DM's extension can size tokens and reuse art. It omits HP, AC, conditions, scores, notes, stat blocks and unrevealed names. The extension keeps the bridge in its background page (`background_url`), polls the table every 2 seconds and shows it in the popover over a `BroadcastChannel`. Only a GM's background page claims a bridge. The extension is published from `owlbear/` to the `gh-pages` branch by `.github/workflows/owlbear-pages.yml` and served at `https://gtarne2.github.io/DnD-combat-tracker/`, the only origin the bridge page answers.

Stage O2 puts tracker rows on the Owlbear map. All scene writes run in the DM's background page (`owlbear/tokens.js`), because Owlbear lets every player read item metadata. A linked token's metadata under `com.aurora-tracker/link` holds only the tracker room ID, row ID, kind, whether the extension created the token, and the last reveal state it applied. Names, member IDs and stats never go into metadata. Tokens the extension adds use the art chosen once per monster template, player or companion through Owlbear's asset picker, saved in the DM's browser, or a bundled placeholder. An unrevealed enemy is added hidden and named "Enemy". Large and bigger templates span 2 to 4 cells. After each 2-second table poll, `syncTokens` renames created tokens, shows a token on reveal, hides it again only if the extension created it, attaches a "Down" label when an enemy reaches 0 HP, and deletes the token of a removed row. Tokens the DM placed and linked by hand from the context menu are never renamed, re-hidden or deleted, only unlinked. Tokens linked to another tracker room are ignored. Because links live in scene metadata and the tracker keeps row IDs across a resume, links survive a helper restart once the DM pairs again. Owlbear players are matched to tracker players by unique name, and the DM can change a match in the popover. Matches are kept in the DM's browser, keyed by tracker room, for the spell stages. Adding and removing tokens lives in the extension popover rather than the DM dashboard, because only the extension can write to the scene.

Stage O3 adds spell templates. The sheet reads an area from Aurora's range text, such as "Self (15-foot cone)", or from the description, such as "20-foot-radius sphere" or "a line 100 feet long and 5 feet wide" (`combat::spell_area`), and writes it as `data-spell-area`. In a DM room, a player who has joined the encounter sees an Owlbear template section in the cast dialog. It is filled from the parsed area and can be corrected or added by hand: shape, size, line width, the row to point at, and when to remove it. The template travels as a `place_template` fight edit, so it reuses the existing initiative path from sheet to host. The fight keeps up to six templates per player. A template is dropped when the caster's row goes, when the encounter ends, or, for "end of my turn", when the caster's turn ends. The sheet clears a concentration template itself once its concentration ID is no longer active, and lists the player's templates on the combat rail with a remove button. Template edits are player-only and bump the fight revision, so they can make a concurrent DM edit retry. The sheet retries its own template edits for a few seconds after a revision conflict, because a joined sheet's view of the room can lag behind the host.

The table feed lists templates with the caster's row, so the DM's background page can place them (`owlbear/template-sync.js`). Cones, lines and cubes start at the edge of the caster's token and point at the aimed token, or north. Spheres and cylinders sit on the aimed token, or just north of the caster. Emanations surround the caster's space and are attached to the token so they move with it. Sizes use the scene's grid scale and dpi. Every template is a closed curve, which keeps the shapes exact and gives O4 one polygon type to test. The DM's page asks the matched player's extension, by `OBR.broadcast`, to draw the template so the player owns it. The player's extension accepts only requests addressed to it from a GM connection, and validates the shape first. If no player is matched, or the player's extension does not draw the template within 4 seconds, the DM's extension draws it. Players can move drawings made by the DM under Owlbear's default permissions. The DM's page removes drawings whose template the room dropped. It remembers which templates it has drawn, in the DM's browser, so a template someone deleted by hand is not drawn again. Template metadata holds only the tracker room and template IDs.

Stage O4 works out who is inside each template (`owlbear/inside.js`). It uses the half-square rule from the 2014 Dungeon Master's Guide. A grid square counts when the template covers at least half of it, and a creature is inside when any square of its space counts. The DM's extension takes each drawing's points with its position, rotation and scale. It clips the drawing against each grid square in its bounds and measures the covered area. A token's space is its cell count across, from its image size, image dpi and scale, centred on the token. A creature smaller than a square uses the square its centre is in. The caster is left out of their own emanation. Square grids only: on a hex grid the popover says so and no suggestions are sent.

Stage O5 resolves area damage through the DM, because only the DM can send damage offers. The sheet's parser reads the save ability, whether a success halves the damage, and the damage type from the spell text, and the cast dialog stores them with the dice on the template. The caster's rail rolls the dice and sends `send_area` with the amount and confirmed targets, which is the first confirmation. The room keeps up to six templates and a short list of queued areas (`Fight.areas`, the last 10 resolved). The DM dashboard rolls each save with Assist when the monster's save bonus, or the player's shared character details, give a bonus, and applies immunity, resistance and vulnerability for the damage type, treating the spell as magical so a clause that covers only nonmagical attacks is skipped while a plain clause beside it still applies (`monsterAssist.defense`, shared with quick damage, R75). All failed and All saved set every non-companion outcome in one click. Apply (`apply_area`, the second confirmation) is handled at room level: it lowers enemy HP and sends each targeted player a damage offer whose action ID is derived from the area and member, so a retry cannot double it. Companions are not changed, since their HP belongs to their player's sheet. Zone spells are not rolled automatically at turn start. The dashboard notes when the current creature is inside a concentration template, and the caster sends the area again. Healing areas are out of scope.

Save spells without a template (R76) use the same queue. `send_spell` carries the spell name, damage type and save itself, since there is no template to read them from, and is stored as a queued area whose template ID is nil. Everything after the queue (Assist saves, defenses, Apply, offers, the record of the last 10) is shared, so the two paths cannot drift. The offer source says "(spell)" instead of "(area)". The cast dialog offers it only when the sheet has joined the encounter and the spell has a save, a DC and damage, and hides it when a template is being placed, which keeps one confirmation path per cast.

Playtest round one (R65–R67). Enemy numbering happens when rows are added (`number_duplicates` in `src/party/initiative.rs`), so names stay stable when one is removed, and both the DM's name and the alias are numbered against earlier rows only. Hidden enemies now send their alias in the table feed, since Owlbear does not show hidden items to players. The bridge window says hello every second while its partner frame is closed or silent for 4 seconds, and the extension keeps a second bridge window as a spare, so an Owlbear reload or a second window no longer needs a click. A LAN long poll now also ends when the projected view changes, which carries map reports (who is inside) to the caster within about a quarter second. The launcher keeps a DM `PartySession` and its dashboard bridge in `hostedParty` when the same PC joins as a player or opens a sheet. Player action tracking defaults on only while the DM's shared initiative drives the sheet (`partyClock`), because solo play has no turn boundaries to reset it.

Playtest round two (R68–R70). A companion that acts on its owner's turn has no row, so the table feed gives it a stable map ID (`companion_map_id`, the owner row's ID mixed with the companion's sheet ID) and lists it as a `shared` companion row. Inside reports and the player's view accept these IDs, and the owner's row tells its sheet which ID belongs to which companion. A template can name an `anchor` companion, and the feed then centres it on that companion's row or map ID. The Protector aura is such a template with `lasts: removed`, placed and cleared by the owner's sheet, so its inside list comes from the same half-square check as spells and needs no new bridge action. The sheet resubmits its initiative entry (same score, new companion list) when its available companions change during a joined fight, which is how a summon reaches the DM. The Eldritch Cannon feature is forced into the Action group because its text also names the activation bonus action, and `activation_in` refuses text that names two groups.

Rings and concentration (R74). Ring markers copy the Colored Rings extension's construction (a `CIRCLE` shape sized to the token's grid footprint, stroke 5, no fill, attached and hit-disabled, each further ring 10% smaller), but carry this extension's own marker metadata so the two extensions never fight over each other's rings. The DM's concentration list compares each row's HP between dashboard refreshes instead of hooking every damage path (quick HP, strikes, area damage, offers), so no path can miss it. The sheet's reminder is a non-modal dialog, so it never blocks the sheet or another dialog.

Results go to the helper through a fourth bridge action, `inside`. It is the bridge's only write, and is token-checked like the others. The extension sends `[{template, rows}]` when the result changes, half a second after the scene settles, and every 10 seconds in case the helper restarted. `RoomService::report_inside` keeps these reports in memory per room, outside the journal and the fight revision, because tokens move constantly. It drops reports for unknown templates and rows outside the encounter. Polls add an `inside` list to each template in the combat view. A player's list leaves out unrevealed enemies, so a suggestion never reveals a hidden creature. The DM's list is complete. The caster's combat rail shows each template with the map's suggestion as checkboxes, and "Add someone else" for other visible rows. The list follows the map until the player edits it, then offers "Use the map's list" when the map changes. Confirm targets sends a `confirm_template` fight edit, which stores the confirmed rows on the template for O5 to apply. The plan placed this list in the cast dialog. It lives on the combat rail instead, because the template exists only once the cast is confirmed, and the player moves it afterwards.

## Mechanics overlay

`src/mechanics.rs` embeds `content/mechanics/overlay.json`, the tracker's own table of spell template data (R71). Each entry has a spell name, a rules edition (2014 or 2024), the 5etools book codes that print that version, an optional area (shape, size, line width), an optional colour and the damage types. The file also maps book names, as Aurora and 5etools print them, to those codes, plus a damage-type palette. It holds no rules text, so shipping it adds no book content. A player only benefits from an entry for a spell they imported.

Matching normalizes names and books to lowercase letters and digits, so "Player’s Handbook" and "Player's Handbook" agree. An imported spell with a book the overlay knows uses the entry listing that book, which keeps 2014 and 2024 versions apart (Sleep is a 20-foot sphere in one and 5 feet in the other). A book the overlay does not know, such as homebrew, gets no entry and keeps the area read from its text. A spell with no source falls back to the 2014 entry, Aurora's default rules. When an entry matches, its area replaces the one `combat::spell_area` read, because entries come from structured data or were checked by hand; spells the overlay lacks, such as a teleport's reach, keep the text reading. The colour is the entry's own, then the palette colour of the damage type the description names, then of the entry's first damage type.

`tools/build-mechanics-overlay.cjs <5etools-src>` rebuilds the overlay. It reads only structure from `data/spells` (area tags, range type and distance, damage types, sources) and the measurement phrase of the description, writes no text, and then applies `content/mechanics/curated.json`, the hand-reviewed walls, odd shapes and colours. 255 entries cover 257 area spells (81 reviewed); Conjure Constructs and Death Armor have none yet. The sheet writes `data-spell-colour` and `data-spell-overlay` beside `data-spell-area`. The cast dialog sends the colour with the template (`AreaTemplate::colour`, `#rrggbb` only), and the Owlbear extension fills with it and outlines with the caster's colour. Three hand-written sections follow the spells, matched the same way by name and book (R72). `features` gives an action group for a feature whose import has no time setter or sheet action; it ranks after a summon feature and before the guess from the description, so the import's own timing still wins. `summons` describes Eldritch Cannon: shared AC, an HP formula, speed, command and duration, and three variants with one-line summaries the tracker wrote. `companion::is_summon` recognizes the cannon by the original ERLW ID or by an overlay match, and the option row carries `data-summon-feature` so the Create control no longer depends on the Aurora ID. `companion::apply_overlay` fills only empty fields of imported variants and adds missing ones with IDs `<feature ID>_<VARIANT>`, which keeps the `ELDRITCH_CANNON` and `_PROTECTOR` checks in the sheet's scripts working. `companions` holds HP formulas (`base + per_level × class level + ability modifier`, at least 1) for companions whose import gives text such as "five times your artificer level"; the class level comes from the class definitions' names, or the profile's Class field. Spell-level summons (Summon Beast and similar) are not covered yet.

Template looks (R73). The overlay's `spell_looks` maps a spell name to a look; `Overlay::template_look` falls back to the damage type. The sheet writes `data-spell-look`, the cast dialog sends `AreaTemplate::look` (lowercase letters only), and the table view passes it to the extension. `owlbear/template-art.js` turns a look into an outline style and art: an image from `owlbear/effects/<look>-<disc|cone|rect|line>.png`, or three nested fill curves for a fade. The art is attached to the template curve with `disableHit`, sits one zIndex below it and carries only `com.aurora-tracker/template-art` metadata, so dragging, rotating, the inside check and the hand-delete rule still see one item per template. `syncTemplates` deletes art whose template is gone. The textures are procedural, built by `tools/build-template-art.py` (numpy and Pillow), so no art is licensed. Owlbear's SkSL effects could animate looks, but they are local-only and experimental, so each viewer's extension would have to draw them; that is left for later.

## Aurora content import

The Rust importer reads a UTF-8 character save and local content XML files. It resolves equipment, spells, build selections, and companions by the exact Aurora content ID. Each saved reference retains its ID and label with an optional definition. A missing definition leaves the reference available for display or later correction. File read errors and malformed XML fail the import.

Callers pass content files in Aurora load order. The last definition with the same ID wins, including within one file, and targeted `append` entries contribute rules and supports in file order. Each resolved definition records its source file and published version when present. It keeps the definition's description markup, sheet text, setters, rule attributes, and other content as data.

The launcher stores selected folders alongside individual file paths. The CLI rescans each folder on import, recursively collects XML files, and expands the folder in sorted path order at its position in the source list. A separately listed file after that folder takes precedence for duplicate definitions.

The import catalog follows exact IDs named by grants, ID-based selections, and embedded descriptions. This makes related options such as the Artillerist's cannon variants available even when the save names only the parent feature. The catalog records unavailable targets and visits each ID once. Saved selections retain their own lists, and rule data retains conditions such as levels and support expressions for later evaluation by the app.

## Saving currency

The importer reads copper, silver, electrum, gold, and platinum from `build/input/currency` and locates their values in the original UTF-8 save. Inventory replaces the edited values in a browser download, preserving the surrounding XML and file encoding. Missing denominations start at zero and receive their currency elements on export.

Standalone previews include the character XML needed for export. Pending edits live in the browser view preferences by denomination. **Export Aurora copy** downloads a new `.dnd5e` file. The tracker stores encounter state separately in the browser.

## Re-importing a character

A Rust character session keeps the Aurora snapshot and its source paths alongside tracker-owned encounter state, layout, and pins. Re-import reads the same save path so a character rename leaves the session attached. The session loads the entire new snapshot before applying it. A failed read or parse leaves the previous snapshot, sources, and tracker state available for retry. Callers can supply an updated list of content files in Aurora load order.

Pins for saved equipment, spells, build elements, and companions follow the exact Aurora content ID in the corresponding list. Pins for linked options follow IDs in the reachable definition catalog. An unresolved ID still qualifies while the refreshed save or catalog references it. Re-import removes pins whose targets disappear and returns them in their previous order. It preserves the order of the remaining pins, tracker-owned pins, and the encounter and layout values.

The list and inspector call the same handlers for casting, consumable use, and tracked features. Casting records the selected slot and any concentration change in one encounter update. An attack records the weapon and round in the existing undoable encounter state. Players resolve attack rolls and damage at the table. A local table rule can suppress imported concentration for Guidance. Long rests restore known maximum HP. Short rests apply the entered healing. Both record healing in the same update as the rest.

The browser keeps manually tracked ability uses, shared resource costs, toggleable effects, and imbuements in the undoable encounter snapshot. Pool recovery comes from explicit short or long rest labels or a user setting. A rest updates recovering resources and timers together. Long rests can also update local prepared-spell and imbuement selections. Always-prepared spells and cantrips stay outside preparation editing. The tracker recognizes Heat Metal and Eldritch Cannon follow-ups and can surface a user-entered bonus action while a tracked ability is active. It records use and leaves damage or other rule resolution to the player.

Tracked abilities store optional custom text and a stable link to an imported option or an ongoing effect ID. The browser displays imported rules from the same rendered option used by the Combat inspector. Passive features suppressed in Combat and known infusions are also available to reference. Effect links read the current shared effect record and preserve the tracked ability when the effect is ended or removed. The existing feature-use binding remains independent of the optional reference. Legacy cards retain their notes and inherit the reference from their existing feature binding unless the user clears it.

Custom effects belong to stable character, companion, or combatant IDs. Each has a name, notes, and an expiration rule. Round durations tick when initiative wraps, advancing the in-game clock by six seconds. Explicit elapsed time advances time-based effects and concentration. Turn-boundary durations count the matching starts or ends of the selected participant's turn. A companion acting with its owner uses the owner's turn.

Condition is a display type available with any expiration rule. The cards show the effect name, duration or boundary, and any entered mechanical modifier. The main character header shows active concentration and compact indicators for the owner's effects. Companion cards and the right-side panel read conditions and remaining duration from the same effect records.

Advancing initiative processes the outgoing end boundary, any round rollover, and the incoming start boundary in one update. Reordering initiative leaves durations as they were. Expired or manually ended effects are available for review and editing, and can be removed. Effects are included in the same saved encounter and undo history as initiative.

The Journal page keeps both legacy editors at their original keys and stores dated entries in the view preferences. Journal entries can link to a sheet reference or a stable activity ID in the current or an archived encounter. The player can search entry text, dates, and link labels. Existing Notes navigation resolves to the combined page.

Cannon shortcuts show imported action descriptions and Artificer spellcasting bonuses when available. A Protector activation records bonus-action use and grants temporary HP to the selected recipients in one undoable update. Companion cards store temporary HP in the same encounter snapshot as their regular HP, with existing cards defaulting to zero.

## Session portability and Combat controls

The version 1 tracker backup contains the encounter, undo history, layout and pins, browser view and corrections, and legacy writing. Restore validates the file and previews what it will replace. It writes to the currently open profile, so the same backup can move progress to another browser profile or Aurora path. Chrome or another supported browser continues to own live storage.

Compact Combat keeps pinned resource pools in the header and moves access to the other pools to a dialog. The layout keeps its saved inspector width and visibility. The compact initiative list reads the same order as roster editing. Owner healing and combatant and companion HP adjustments commit through the encounter transaction. Resource buttons restore keyboard focus after repaint, and follow-up actions participate in the same search as imported options.

Charged equipment uses the stable inventory identity to bind an imported or user-selected pool. Known daily pools currently recover on a long rest. The player can adjust the pool in Manage resources. Slot, ritual, and free-use modes show their tracked costs at cast time. Chosen costs, turn action availability, and concentration changes commit atomically.

The activity log lives in the same undoable snapshot as HP, turns, and resources. Ending an encounter archives a named record with its initiative roster, round, and activity. Starting resets the active record and keeps ongoing character state. Saved roster templates and effect presets live in view preferences. Loading a roster reuses matching participants when possible and adds missing ones. Effect presets retain duration, target, turn, and modifier notes, and unavailable participant defaults can be reviewed before applying.

Optional Action, Bonus Action, and Reaction counters are stored by participant. Usage resets at that participant's next turn start. Companions acting with the owner share the owner's turn boundary, with their own optional counters. Cannon commands use the owner's Bonus Action. An explicit override applies to one use of the selected action type. The standard action handlers check and update these counters in the same transaction as their costs.

## Combat actions, spell targets, and item timings

The Rust projection resolves Extra Attack and Sneak Attack through the same class stat evaluator. The browser charges the optional Action counter once at the start of a weapon sequence. Later strikes can use different weapons. Hit and miss outcomes are attached to the current recorded attack. A player may confirm Sneak Attack once per turn or spend a supported maneuver's shared pool on a hit.

Resolved spell metadata feeds the searchable reaction text, spell filters, and casting dialog. The player selects an incoming event before applying damage, and the reaction list uses prepared spell, slot, and reaction availability. Shield records a temporary effect against the trigger. The player decides the final damage. Supported conditions such as metal armor apply only to the cast being recorded. The tracker logs the chosen advantage and leaves the roll to the player.

Supported target-count clauses are evaluated at the selected slot level. Bless and Moonbeam use participant IDs and the active concentration record. Concentration ending or replacement ends the linked effects in the same transaction. Moonbeam reminders appear when marked creatures start their turns. The player marks which creatures are in the area and resolves saves and damage.

Attunement preferences are saved by stable inventory key and use the exported selection as their baseline when present. The activation check uses that same state on all charged-item surfaces. Explicit dawn formulae use a separate recovery schedule. Advance to dawn updates elapsed time and charges together, with the entered elapsed time independent of the item recovery roll.
